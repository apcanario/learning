01The context window is the one thing you control

Anthropic defines the context window as all the text a language model can reference when generating a response, the response itself included (Anthropic, Context windows, read 15 Nov 2026). Its glossary separates that window from the corpus the model was trained on and calls the window the model's working memory (Anthropic, Glossary, read 15 Nov 2026). Everything in a request counts against it: the system prompt, every message (tool results, images and documents included), the tool definitions, and the output the model writes for the turn, its thinking included (Context windows).

That is the whole interface. The model's trained weights are fixed by the time you use it. What changes from one answer to the next is the text in the window, and most of that text is chosen by you: what you type, paste and attach, the standing instructions you save, the files you put in a project, the tools and connectors you switch on, the skills you install, whether memory is on, and when you start a new chat. The rest is written by the vendor (the product's system prompt) or by the model itself: its earlier replies, and the search and file results it fetches. When an output fails, the first question is what was in the window when it was written.

The tree below sorts what reaches the window by who writes it.

How big the window is (read 15 Nov 2026). On Anthropic's API, Opus 5.5, Sonnet 5.5, Haiku 5.5 and Fable 5.2 each have a 1M-token window and can write up to 128K output tokens in one request (Anthropic, Models overview; Context windows). In the claude.ai chat on a paid plan, the help centre lists 1M tokens for Opus 5.5, Sonnet 5.5, Haiku 5.5 and Fable 5.2, 500K for some older models such as Opus 4.8 and Sonnet 4.6, and 200K for any model not in its table (Claude Help Center, How large is the context window on paid Claude plans?). Part of the window is held back for the reply, so the longest conversation is slightly shorter than the full window (Claude Help Center, How do usage and length limits work?). These numbers change; check them on the vendor's page on the day you rely on them.

A big window is a ceiling. It says how much text can be placed in front of the model, and nothing about how well the model will use it (§2).

The case. Academy (Academy case), a library of self-study courses built by one person with Claude in October and November 2026, is the running example of this course. It is one project by one person: an anecdote, never evidence about AI tools in general. Its method writes each unit in a new chat or a fresh agent context that sees only its brief and the units already filed, and the stated reason is that leaked context is how a course starts repeating itself (Academy case file §2). That rule is a decision about the window: it fixes what the writer can see. Whether it works better than the alternative is untested, because the record holds no unit written without the method (Academy case file §9). Grade: documented practice, in one project.

02Tokens: what you pay with and what the model attends with

What a token is

A token is the smallest unit a language model works in; it can be a word, part of a word, a character or a byte. For Claude, how many characters make a token depends on the model and the language. Claude 4.7 and later models use a tokenizer that produces about 30 percent more tokens for the same text than earlier models, on which a token is about 3.5 English characters (Glossary, read 15 Nov 2026). Anthropic's model page gives the current tokenizer's own conversion: 1M tokens is roughly 555k words or 2.5M Unicode characters, about 2.5 characters a token (Models overview, read 15 Nov 2026; the per-token division is this unit's arithmetic). The glossary gives no figure for other languages, and points to Anthropic's token-counting endpoint for exact counts (same page).

Tokens as cost

The model keeps nothing between turns. Anthropic's API documentation says the Messages API is stateless, so the full conversational history is sent with every request (Anthropic, Using the Messages API, read 15 Nov 2026). The context-window page says the same turn by turn: each turn's input holds all previous history plus the new message, and previous turns are preserved completely (Context windows). The same API page now describes a beta feature, message threads, in which the API keeps the conversation so that a later request sends only the new messages; a thread expires five minutes after its last request (Using the Messages API). That changes what a developer sends over the wire. It does not say the model reads less: on the context-window page, each turn's input still contains the whole history.

The consequence is that cost grows faster than the conversation. Illustrative arithmetic, unmeasured: if every exchange adds about 2,000 tokens, the first turn sends about 2,000, turn 10 sends about 20,000 tokens of history, turn 20 about 40,000 and turn 30 about 60,000. Added up, the first 10 turns send about 110,000 tokens of input, the first 20 about 420,000, and the first 30 about 2,000 × (1 + 2 + … + 30) = 930,000, before any standing layer (system prompt, instructions, memory, skill descriptions) is counted again on every turn.

On claude.ai you see a usage limit in place of a price. Anthropic says usage depends on the length and complexity of your conversations and on the model, features and effort level you choose; that claude.ai, Claude Code and Claude Desktop count toward the same limit; and that tools and connectors are token-intensive (How do usage and length limits work?, read 15 Nov 2026). On the API, the price per million tokens (read 15 Nov 2026) is $4 input and $20 output for Opus 5.5, $2 and $10 for Sonnet 5.5, from $0.10 and $0.50 for Haiku 5.5, and $8 and $40 for Fable 5.2 (Models overview). Output costs five times input on every row.

OpenAI documents the same mechanism for its own API: each request is independent and stateless, and when responses are chained, all previous input tokens are billed again as input (OpenAI, Conversation state, read 15 Nov 2026). The principle holds across vendors; the prices do not.

Tokens as attention

Anthropic's Applied AI team (Prithvi Rajasekaran, Ethan Dixon, Carly Ryan and Jeremy Hadfield) explain why more text is not free even when it fits: a transformer relates every token to every other, which gives n² pairwise relationships for n tokens, so a model has an attention budget that each new token draws down, and context is "a finite resource with diminishing marginal returns" (Rajasekaran et al., Effective context engineering for AI agents, Anthropic, 29 Sep 2025). Anthropic's documentation names the effect: "As token count grows, accuracy and recall degrade, a phenomenon known as context rot" (Context windows, read 15 Nov 2026).

Three kinds of evidence stand behind this, and they measure different things.

  • Peer-reviewed (measured). Liu and colleagues found that performance was often highest when the relevant information sat at the beginning or end of a long input, and degraded significantly when it sat in the middle, even for models built for long contexts (Liu et al., "Lost in the Middle: How Language Models Use Long Contexts", TACL 12, 2024, 157–173). The tasks were multi-document question answering and key-value retrieval. The models were MPT-30B-Instruct, LongChat-13B (16K), GPT-3.5-Turbo, GPT-3.5-Turbo (16K), Claude-1.3 and Claude-1.3 (100K), with Flan-T5-XXL, Flan-UL2, Llama-2 and GPT-4 (8K) in further experiments.
  • Vendor research (measured, by an interested party). Chroma tested 18 models, among them Claude Opus 4, Sonnet 4, Sonnet 3.7, Sonnet 3.5 and Haiku 3.5, and found performance growing less reliable as input length grew; models did not use their context uniformly, and distractors (passages similar to the answer) lowered accuracy further (Hong, Troynikov and Huber, Context Rot: How Increasing Input Tokens Impacts LLM Performance, Chroma, 14 Jul 2025). Chroma sells a retrieval database, a product whose case this finding supports; label it vendor data.
  • Vendor statements (documented, no figure). Anthropic states context rot as a property of its models without a number (Context windows). Google's Gemini documentation says retrieval of a single fact in a long context scores well, that with several facts to find the model does not perform with the same accuracy, and that putting the question at the end of a long prompt gives better results (Google, Long context, Gemini API docs, last updated 15 Oct 2026).

None of these measured Opus 5.5 or any model current on 15 Nov 2026. The direction agrees across all of them: the more text in the window, the less reliably the model uses any one piece of it. How large the effect is on the model you use is unmeasured. Practical consequence (documented practice): Anthropic's team frames the job as finding the smallest set of high-signal tokens that makes the outcome you want likely (Rajasekaran et al.), and Claude Code's documentation asks for instruction files under 200 lines because longer files consume more context and reduce adherence (Anthropic, How Claude remembers your project, read 15 Nov 2026).

03What persists: inside a chat, across chats, and what memory changes

Inside a chat

Inside one chat everything persists, because everything is re-sent (§2). On Opus 4.5 and later Opus models, the API also keeps the model's earlier thinking blocks by default, and they count against the window like any other input (Context windows, read 15 Nov 2026).

A fact can still be lost inside a chat in two ways.

  1. It is in the window and goes unused. That is the attention problem in §2. A rule stated in turn 3 of a 40-turn chat is present and competing with everything written after it.
  2. It is summarised away. On claude.ai, for users with code execution enabled, Claude summarises earlier messages when a chat grows long so the conversation can continue; the help centre says the full history is still kept so earlier content can be referred to (How do usage and length limits work?, read 15 Nov 2026). In Claude Code, as the window fills, older tool outputs are cleared first and then the conversation is summarised; the documentation warns that detailed instructions from early in the conversation may be lost, and tells you to put persistent rules in the CLAUDE.md file instead (Anthropic, How Claude Code works, read 15 Nov 2026). Grade of that advice: documented practice.

Across chats

Across chats nothing persists in the model. A new chat is a new request with a new window, built from whatever the product puts into it. Claude Code's documentation says it directly: each session begins with a fresh context window, and knowledge crosses sessions through two mechanisms, the CLAUDE.md files you write and the auto-memory notes Claude writes itself (How Claude remembers your project, read 15 Nov 2026). claude.ai runs on the same principle with more layers (all read 15 Nov 2026):

  • Profile instructions are account-wide and applied to all your conversations; project instructions apply only to chats inside that project (Claude Help Center, Understanding Claude's personalization features).
  • Project files sit in project knowledge. When a project nears or passes the window limit, retrieval mode switches on automatically: Claude searches the uploaded documents and loads only the most relevant parts, which lets a project hold up to ten times more (Claude Help Center, Retrieval augmented generation (RAG) for projects).
  • Memory, in Anthropic's post of 25 Aug 2026 (read 15 Nov 2026), is on by default on the Free, Pro, Max and Ultra plans; on Team and Enterprise, "admins control availability for their organization" and memory is off for each member until they turn it on. An undated update note on the same post changes that for members of most Team and Enterprise organisations created on or after 31 Oct 2026: memory is on by default for them, and owners can still turn it off for the organisation; nothing changes for organisations created before that date (Anthropic, Claude's memory works everywhere, and you decide what's in it). The help-centre article cited below refused the fetch, so its plan list was not checked. Claude saves memory as individual topics during chats, and an update made in one chat is known in the next. Each project has its own memory: inside a project Claude uses that project's memory and your non-project memory, never another project's. Sensitive topics are not stored by default; incognito chats are not used for memory; deleting a conversation does not delete the memories written from it; and you can open, edit or delete any topic (Claude Help Center, Use Claude's chat search and memory to build on previous context).
  • Chat search, on paid plans, retrieves past chats by search and shows the search as a tool call in the conversation; outside projects it searches all non-project chats, and inside a project only that project's chats (same article).

What a memory feature changes

Memory changes what gets put into the next window. It does not change the model. Every layer above is text that something re-inserts; take the re-insertion away and the fact is gone. Memory is also text written by a model about your chats, so it is open to every failure in this unit: it can be incomplete, out of date or slightly wrong, and once inserted it competes for attention like anything else. How much memory is inserted into a given chat is not stated on the help-centre pages read for this unit.

One path does run from your chats into a model, and it is slow. Since Anthropic's consumer-terms update of 28 August 2025, users of the Free, Pro and Max plans choose whether their chats may be used to improve Claude; the setting applies to new or resumed chats, and data from users who allow it is kept for five years, against 30 days otherwise (Anthropic, Updates to Consumer Terms and Privacy Policy, 28 Aug 2025). That feeds a future training run. None of the documentation read for this unit describes a path by which a chat changes the model you talk to the next day.

The case. In Academy (anecdote), writer agents were lost to container restarts; in one deep dive two writers were lost, and the third resumed from the second's working files (Academy case file §7). The conversation did not survive; the files did. That is the across-chats rule in one event: what you need to outlive a session has to be written somewhere a later window will read.

Diagnostic. When a new chat ignores something you said last week, ask which layer was supposed to carry it into this window, and whether it did. The usual answers: it was said inside another project; memory did not write it, or wrote another version; chat search was not triggered; the project was in retrieval mode and fetched other passages.

04Three kinds of knowledge, and the training cutoff

Trained

Claude's underlying model was pretrained on a large body of text to predict the next word given the text before it, then fine-tuned and trained with reinforcement learning from human feedback to behave as a helpful assistant (Glossary, read 15 Nov 2026). What it learned that way stops at a cutoff. On 15 Nov 2026, Anthropic lists the reliable knowledge cutoff of Opus 5.5, Sonnet 5.5, Haiku 5.5 and Fable 5.2 as June 2026, and points to its Transparency Hub for training-data cutoffs (Models overview). This unit was written five months after that cutoff. Any model lineup, price, plan limit or event after June 2026 is something the model can know only if it reaches the window: you supply it, a search fetches it, or memory re-inserts it.

The claude.ai system prompt supplies the current date at the start of every conversation (Anthropic, System prompts, read 15 Nov 2026). So the model knows what day it is without knowing what has happened since June. That gap produces a characteristic failure: an answer that is correctly dated and out of date.

Retrieved

Retrieval-augmented generation fetches material when the question is asked and passes it into the context window with the question, so that the answer can be grounded in evidence; the model can do the fetching itself through a tool (Glossary). The glossary adds that how well this works depends on the quality and relevance of what is retrieved (same page). Web search, chat search, a project in retrieval mode, a connector pulling a document, Claude Code reading a file: each is retrieval. Retrieval is selection. The model sees the passages that were fetched and nothing else, and the answer is only as current as the page it came from.

The case. In Academy's second audit (anecdote), ten claims in one unit were stale, all from one cause: an independent benchmark published a new index version the day before the unit read its leaderboard (Academy case file §4). The case file does not record how the older figures reached the unit. What it shows is that a fetched figure belongs to a version and a date, which is why this course dates every product fact to the day it was read.

In the conversation

Whatever you typed, pasted or attached, plus everything the model wrote earlier in the same chat. The second half is easy to miss. Each response becomes part of the input for the next turn (Context windows), so a wrong figure the model produced at turn 5 is in the window at turn 25, read on every turn like anything you supplied.

Why the distinction matters

The three kinds look the same in the output. A sentence about last month's price reads the same whether it came from a page fetched ten seconds ago, from a memory note written last week, or from no source at all. The only way to tell is to know what was in the window. A claim that points to a fetched source can be checked against it; a claim that points to nothing came from training, or was produced without a basis (§7).

05Why the same prompt gives different answers

Sampling is the design

At each step the model computes a probability distribution over possible next tokens, and one is drawn from it. Temperature is the parameter that controls how random that draw is: higher gives more varied output, lower gives more conservative, more probable phrasing (Glossary, read 15 Nov 2026). Sampling is deliberate. Holtzman and colleagues showed that decoding by likelihood alone produces text that is bland and repetitive, and proposed sampling from the most probable part of the distribution ("nucleus sampling") to get diverse text without losing fluency (measured; Holtzman, Buys, Du, Forbes and Choi, "The Curious Case of Neural Text Degeneration", arXiv:1904.09751, revised 14 Feb 2020; cited here as the arXiv version, since the conference version could not be checked).

On current Claude models you no longer set this yourself. On 15 Nov 2026, Anthropic's API documentation says the temperature, top_p and top_k parameters are not supported on Claude 4.7 and later models, that a non-default value returns an error, and that you should use prompting to guide behaviour instead (Using the Messages API). None of the claude.ai help pages read for this unit offers a sampling setting either. The randomness is still there; you just do not hold the dial.

Even fixed settings vary

Anthropic's glossary states that even with temperature set to 0, results will not be fully deterministic, and identical inputs may give different outputs across calls, on Anthropic's own service and through cloud providers (Glossary). The glossary does not give the cause. One lab gives a candidate. Horace He, with colleagues at Thinking Machines Lab, sampled 1,000 completions at temperature 0 from an open-weights model (Qwen3-235B-A22B-Instruct-2507) for one prompt, and got 80 distinct completions; the most common appeared 78 times, and the completions first diverged at token 103. He traced the variation to computations whose results depend on batch size, which varies with server load; with batch-invariant kernels, all 1,000 completions were identical (He, Defeating Nondeterminism in LLM Inference, Thinking Machines Lab, 10 Sep 2025). Grade: measured, in a lab blog post that is not peer-reviewed, on a non-Anthropic model and serving stack. Whether the same cause dominates on Anthropic's service is not stated by either source.

The divergence point is the useful detail. Once one token differs, every later token is conditioned on a different history, so a small early difference becomes a different answer.

Usually the prompt was not the same

The more common reason two runs differ is that the window differed. Between two chats with the same typed prompt, the system prompt carries a new date and is periodically updated (System prompts); memory may have been updated in between, and chat search may return other chats (Use Claude's chat search and memory); a project in retrieval mode may fetch other passages (RAG for projects); and Opus 5.5 thinks adaptively, always on, so the amount of reasoning placed in the window varies with the request (Models overview; Context windows, all read 15 Nov 2026). The model behind a name can also change. OpenAI's prompting guide warns that different snapshots of models in the same family can produce different results, and advises pinning production applications to a specific snapshot (OpenAI, Prompt engineering, read 15 Nov 2026).

The case. In Academy (anecdote), a session's model named "fable" resolved to a newer version than the method names, so the checks it ran were recorded as owed again on the named version (Academy case file §7). Same instruction, different model.

What this means for checking. One good answer is one draw. It shows the window can produce a good answer; how often it does stays unknown until there are more draws. Anthropic's own guidance lists running the same prompt several times and comparing the outputs as a way to spot hallucinations, since inconsistency between runs can signal them (Anthropic, Reduce hallucinations, read 15 Nov 2026). Grade: documented practice (vendor), unmeasured on its page.

06System prompt, project instruction, user message

All three are text in the same window. They differ in who writes them, where they sit and how far they reach.

Layer Written by Reaches Source (read 15 Nov 2026)
claude.ai system prompt Anthropic Every claude.ai and mobile-app chat; not the API System prompts
Profile instructions You All your conversations Personalization features
Project instructions You Chats inside that project only Personalization features
Skill name and description The skill's author Every chat where it is installed; the body loads only when triggered Agent Skills
User message You This turn, then every later turn of the chat Context windows

The system prompt sets the frame. Anthropic publishes the claude.ai version and says it gives Claude up-to-date information such as the current date at the start of every conversation, encourages certain behaviours, is periodically updated, and that those updates do not apply to the API (System prompts). On the API the developer writes the system prompt, and a system message added partway through a conversation has the same authority as the top-level one (Using the Messages API). Authority comes from the role a piece of text is given. When it arrives does not change it.

Project instructions and profile instructions are your standing orders at two scopes. The help centre says the personalisation features can be used independently or in combination, and states no order of precedence between them (Personalization features). Two consequences follow. A rule repeated in two layers is paid for twice on every turn. Two layers that disagree leave the model to settle the conflict with no documented rule. OpenAI, by contrast, documents an order for its API: developer messages are prioritised ahead of user messages (OpenAI, Prompt engineering). Neither vendor's documentation read here says how its consumer chat app ranks a project's instructions against your account-wide ones.

Skills sit across the layers. On 15 Nov 2026, Anthropic's documentation says only each skill's name and description load at startup, about 100 tokens a skill, placed in the system prompt; the body of its SKILL.md, under 5K tokens, enters the window only when a request matches the description; and bundled files load only when read (Anthropic, Agent Skills). The description is what your request is matched against (same page). Twenty installed skills therefore cost about 2,000 tokens in every chat, on Anthropic's per-skill figure, and each one fires on its description alone.

The user message is the request itself. Once sent, it is part of the history re-read on every later turn (§2).

None of these is enforced. Claude Code's documentation says Claude treats its instruction files as context and that they are not enforced configuration; to block an action whatever Claude decides, it points to a hook, a script that runs outside the model; and it says the more specific and concise the instructions, the more consistently Claude follows them (How Claude remembers your project, read 15 Nov 2026). The page is about Claude Code's files. Applying it to every instruction layer is this unit's inference, on the ground that every layer reaches the model the same way, as text in the window (§1). Every instruction raises the probability of a behaviour. None guarantees it.

The case. A structure audit of Academy itself (anecdote) made seventeen findings, among them project instructions that carried procedures and paraphrased the method file (Academy case file §7). A paraphrase in one layer and the original in another is the two-layer problem above: the same rule in two wordings, with nothing to say which wins. BW4 works through that audit.

07Fabrication follows from how the text is produced

A language model writes by predicting the next token from the text before it (§4, §5). Nothing in that step consults a store of facts. When the window holds a source, the most probable continuation tends to follow the source; when it does not, the most probable continuation is whatever reads like an answer. A fluent, specific, wrong sentence is therefore an ordinary output of the mechanism, produced the same way as a right one. Three lines of evidence support treating it that way.

  • A statistical argument (preprint). Adam Tauman Kalai, Ofir Nachum, Santosh Vempala and Edwin Zhang argue that hallucinations originate as errors in binary classification: if incorrect statements cannot be told apart from facts, hallucinations in pretrained models arise through natural statistical pressures. They argue that they persist because training and evaluation procedures "reward guessing over acknowledging uncertainty" (Kalai, Nachum, Vempala and Zhang, "Why Language Models Hallucinate", arXiv:2509.04664, 4 Sep 2025). The paper is a preprint, and its argument is theoretical, with no new measurement on a current Claude model.
  • A mechanism observed inside a model (vendor research). Anthropic's interpretability team reports that in the model it studied, a circuit that declines to answer is on by default, and a feature for known entities inhibits it; hallucinations occur when that known-entity feature fires on something the model recognises without actually knowing, suppressing the default (Anthropic, Tracing the thoughts of a large language model, 27 Mar 2025). The article's introduction says its companion research studied Claude 3.5 Haiku; the hallucination section does not name its model. Transfer to the model you use is this unit's inference.
  • The vendor's own statement (documented). Anthropic's guide says even the most advanced models, Claude included, can generate text that is factually incorrect or inconsistent with the given context, and that its techniques reduce hallucinations without eliminating them (Reduce hallucinations, read 15 Nov 2026).

The practical consequence is a change of posture. A fabrication is a property of every unchecked output, present at some rate, and the rate is what you manage. Anthropic's guide lists ways to lower it (documented practice, vendor): give the model explicit permission to say it does not know; for long documents, have it extract word-for-word quotes before doing the task; have it cite a quote for each claim and retract any claim it cannot support; and tell it to use only the documents provided (Reduce hallucinations). The page says the first "can drastically reduce" false information and gives no figure; treat the size of the effect as unmeasured.

Fabrication also covers more than invented sources. A real page cited for something it does not say, a figure carried to the wrong thing, a qualifier the source never wrote: each is text completed past what the window supported.

The case (anecdote). Of 36 Academy units given a fresh check before filing, 28 had at least one error in the writer's handed-in draft, with 58 errors across the 36. The kinds the reports name include a figure the cited page does not carry, an author named wrongly, a quotation the page does not hold, and a product fact that differed between two of the vendor's own pages (Academy case file §5). The first audit of three marketing units found 23 of 91 claims failing and nothing invented; the pattern it named was qualifiers the source does not carry (Academy case file §3). These counts come from one project, written by one model family, checked by others; they say nothing about rates elsewhere. They do show a shape. None of the kinds of error the reports name is an invented source, and in the one audit that counted, nothing was invented: a check for made-up sources alone would have caught none of those 23 failures. How to check by sample is BW6.

08The layers of a current assistant: a map

Every feature of a current assistant is a way of deciding what enters the window, when, and who chose it. The map below names the layers this course uses; later units fill them in. Product behaviour is as read on 15 Nov 2026.

Layer What it puts in the window When Source
Chat Your messages, attachments and the model's replies so far Every turn, all of it Context windows
Project Project instructions; project files, loaded whole or, in retrieval mode, the passages a search returns Every chat in the project Personalization features; RAG for projects
Memory Notes a model wrote about earlier chats; past chats, when chat search runs Next chat, as the app inserts them; search results when searched Chat search and memory
Tools and connectors Results of a web search, a file read, or an action in a connected service Only when called, then for the rest of the chat Use connectors; How Claude Code works
Skills A name and description per skill; the body and files on trigger Description always; body when a request matches Agent Skills
Agents Whatever the agent's own tool calls bring in, in a loop Throughout a task; a subagent in its own window, fresh unless forked from the conversation How Claude Code works

Notes on the rows:

  • Tools and connectors. Anthropic's help centre says connectors let Claude access your apps and services, retrieve your data and take actions in them; custom connectors use the remote Model Context Protocol (MCP) (Claude Help Center, Use connectors to extend Claude's capabilities, read 15 Nov 2026). In Claude Code, MCP tool definitions are deferred by default, so only tool names and server instructions take up context until a tool is used (How Claude Code works). Every result a tool returns is new text in the window.
  • Agents. Claude Code describes its working cycle as an agentic loop: gather context, take action, verify results, repeated, with tools that read and edit files, run commands and search the web; the model reasons and the surrounding harness supplies the tools and manages what the model sees. A subagent works in its own context window and hands back a summary (How Claude Code works, read 15 Nov 2026). An agent is the same model reading the same kind of window; what differs is that it fills much of that window itself, with the results of its own actions.
  • What none of the layers does. None of them changes the model's weights (§3). Each puts text in front of it.

09Reading a failed output

When an output fails, the model in §1 to §7 gives five questions, asked in this order because each is cheaper to answer than the next.

  1. Was the needed fact in the window? If it lives only in a past chat, another project, a file nobody attached or your head, the model never had it (§3, §4).
  2. Was it buried? If it was there, how much else was there with it, and where did it sit? Long windows degrade recall, and a long chat may have been summarised (§2, §3).
  3. Did it come from a source, or from training? If no source in the window supports the claim, it came from trained knowledge, which stops at the cutoff, or from nowhere (§4, §7).
  4. Do two layers disagree? If the system prompt, your standing instructions, a skill and your message pull different ways, nothing documented says which wins (§6).
  5. Was it one draw? Run it again in a fresh chat. If the answers differ materially, neither is reliable on its own (§5).

Grade: stated opinion (this unit's ordering, built on §1 to §7). Each answer points to a different change: put the fact in a layer that re-inserts it; trim the window or start a new chat; supply the source and ask for quotes; keep each rule in one layer; run it again and check a sample. The decision below draws the same order.

The diagnosis table at the end of this unit turns these five questions into symptoms you can recognise, with the change each one points to and the unit of this course that treats it.

Part 1 · The five-minute model, on the Academy case

The assistant does not remember anything. Each time a message is sent, the app sends the model one long piece of text, and the model writes its reply by reading that text. That text is the context window. It holds the vendor's own instructions, any standing instructions, the files of whatever project the chat sits in, any notes the app keeps, the whole conversation so far, and the new message. The model reads all of it, writes a reply, and keeps nothing. On the next message the whole lot is sent again with the new message on the end.

So the only way to change what the model does is to change what is in that text. The model itself is fixed. It was trained on a huge amount of writing to predict the next word, then trained further to act as an assistant, and what it learned that way stops at a cutoff: for the current Claude models, June 2026. Anything after that it knows only if something puts it in the window: someone pastes it, a search fetches it, or a memory note carries it. In Academy, ten claims in one unit went stale at once: an independent benchmark had published a new index version the day before the unit read its leaderboard. A fetched fact belongs to a version and a date, which is why every product fact carries the date it was read.

What looks like memory is re-insertion. The app writes notes about earlier chats and puts some of them into the next window; a project puts its instructions and files into every chat inside it; Claude Code reads its instruction file at the start of each session. If a fact was never written to one of those places, a new chat has never heard of it. Academy lost two writer agents to container restarts; the third picked up from the second's working files. The conversation was gone. The files were still there.

The text is measured in tokens, a few characters each. Tokens are what it costs: the whole conversation is re-sent every turn, so a long chat costs more with every message. Tokens are also attention: the more text there is, the less reliably the model uses any one piece of it, especially what sits in the middle. A bigger window raises the ceiling on how much fits. It does nothing for how well the model uses what is there. Academy writes each unit in a fresh context that sees only its brief and the units already filed; the reason it gives is that leaked context is how a course starts repeating itself.

The same request can get different answers. The model draws each next word from a spread of likely options, and even with the settings fixed, the servers do not return exactly the same result every time. More often, the two windows differed: a new date, an updated note, a different search result, a different model behind the same name. In Academy, a session's model, called by the name the method uses, resolved to a newer version than the one the method names. One good answer is one draw. It shows the setup can get it right and says nothing about how often.

Instructions sit at different levels: the vendor's in every chat, the account-wide ones in every chat of that account, a project's only in that project, and then the message itself. All of them are text in the same window. None is a hard rule; each makes a behaviour more likely, and shorter, more specific instructions are followed more consistently. When two levels say the same thing in different words, nothing documented says which one wins. Academy's own structure audit found project instructions that paraphrased the method file.

The model will sometimes write things that are not true, because it writes what is probable given the text in front of it, and when no source is there, a plausible answer is what comes out. In Academy, 28 of 36 drafts had at least one error when a separate checker read them against their sources, and none of the kinds of error named was an invented source: they include a figure the page does not carry, a quotation it does not hold, an author named wrongly. That is one project, and it proves nothing in general; it is why 36 of Academy's units got a fresh check of every cited claim before they were filed.

When something goes wrong, ask five things in order. Was the fact in the window? Was it buried? Did it come from a source or from training? Do two instructions disagree? Was it one draw? Each has a different fix.
